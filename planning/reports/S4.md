## Timing: `await scan()` vs render

`BeforePayGuardian.scan()` returns the controller promise. That promise settles after `onResult` / `onError` has run `panel.update(…)` and `pip.update(…)`. That is a **DOM update** (those functions returned). It is **not** first paint, layout, or CSS animation.

Use two clocks. Never label the first as paint.

### 1. Scan-await (DOM update) — official scan timing

In the **content-script** JavaScript context on the demo, unpacked extension loaded:

```js
const t0 = performance.now();
await BeforePayGuardian.scan();
const scanAwaitMs = performance.now() - t0;
```

Includes observation + `collectEvidence` + `evaluate` + `update()` returning. Record `getAssessment().scanId`. Five runs, min/median/max. Paths: `suspicious-shoes`, `matching-shoes`; one rescan set.

Helper: `tests/performance/probes/scan-timing.js`.

### 2. Render after scan — reported separately

After `await scan()`:

```js
const tDom = performance.now();
await new Promise((r) => requestAnimationFrame(() => requestAnimationFrame(r)));
const renderAfterScanMs = performance.now() - tDom;
```

Double-rAF approximates the next paint after the DOM update. If a `paint` / `beforepay:*` performance entry exists, record it **in the render table**, not the scan-await table.

Do not add those two numbers and call the sum “scan time”.

Observations (not invented SLAs):

| Observation | Owner (use build-report file) |
| --- | --- |
| Large `scanAwaitMs` with no network | `evaluate` / `collectEvidence` file |
| Small `scanAwaitMs`, large `renderAfterScanMs` | `mountPip` / `mountPanel` file, or CORE mount |
| Times growing across rescans | CORE lifecycle |
| `scan()` hangs past 6000ms without error UI | CORE controller |
